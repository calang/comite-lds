# Uso de la API de WhatsApp para el comité
Creado el 2026-07-12

## Pregunta

actualmente usamos WhatsApp (WA) para preguntas de vecinos y contestación con recomendaciones entre los mismos. nuestros grupos de WA son creados con cuentas personales, no corporativas. yo quisiera que las conversaciones con estas consultas se pudieran resumir y recordar de manera que los miembros del comité pudieran preguntar a un agente de IA por respuestas que se hayan dado en el pasado, sin tener que recorrer largos chats anteriores. ¿en qué forma recomiendas realizar esto, en el contexto de este proyecto, donde podríamos combinar herramientas escritas en Python con algún agente de IA particular y sencillo que pudiéramos desarrollar para apoyar al comité (no para reemplazar la interacción entre vecinos)?

## Respuesta

Antes de pensar en la arquitectura, hay una restricción importante que condiciona todo: **las cuentas personales de WhatsApp no tienen API oficial**. La WhatsApp Business API (Cloud API) requiere un número dedicado y verificado como negocio — no funciona sobre el número personal que ya usan. Y las librerías "no oficiales" que automatizan WhatsApp Web (whatsapp-web.js, Baileys, etc.) sí funcionan con cuentas personales, pero violan los términos de servicio y arriesgan que Meta banee el número que hoy usan para comunicarse con los vecinos — un riesgo que no se debería tomar con la herramienta de contacto real del comité.

**Recomendación**: no automatizar la extracción. WhatsApp ya tiene una función nativa de exportar chat (Ajustes → Exportar chat → genera un `.txt`). Alguien del comité la corre periódicamente (ej. semanal) y sube ese archivo al repo o a Drive. Un script Python simple (en `scripts/`) lo parsea, lo resume por tema/fecha con un LLM, y guarda el resultado como Markdown fechado — similar a como ya manejan `agenda.md`. Luego Claude (o un agente sencillo) responde preguntas de los miembros del comité leyendo esos resúmenes acumulados, sin tocar WhatsApp de forma automática ni recorrer chats completos.

**El tradeoff principal**: esta ruta es 100% segura (no toca los términos de servicio, cero riesgo de baneo) pero depende de un paso manual recurrente — alguien tiene que exportar y subir el archivo. La alternativa — Business API oficial con número dedicado — automatizaría todo el flujo, pero exige crear y verificar un número de negocio aparte del personal, con el costo/fricción que eso conlleva, y probablemente no vale la pena para el volumen de un comité vecinal.

Se recomienda empezar con el export manual + resumen periódico, y solo evaluar la Business API si ese paso manual se vuelve un cuello de botella real.

## Pregunta

¿qué tan complicado es crear una cuenta business con WA? ¿En qué consiste el proceso de verificación?

## Respuesta

Hay que distinguir dos cosas, porque tienen procesos muy distintos:

**1. App de WhatsApp Business (la app normal, gratis)** — sin relación con la automatización. Se instala como cualquier WhatsApp, solo pide verificar el número por SMS/llamada, igual que una cuenta personal. No requiere verificación de negocio ante Meta. Pero esta app no tiene API programable — es solo para uso manual desde el teléfono, no sirve para que un agente de IA la use.

**2. WhatsApp Cloud API (lo necesario para automatizar)** — el proceso real es:

- Crear una cuenta de **Meta Business Manager** y registrar la app en Meta for Developers.
- Verificar un **número de teléfono dedicado** (no puede ser el personal que ya usan en el grupo).
- Opcionalmente, completar la **"Business Verification"** de Meta: subir documentación legal (RUC/identificación tributaria, documentos de constitución, comprobante de dirección) donde el nombre y dirección coincidan exactamente entre Meta Business Manager, el sitio web y los documentos. Toma entre 2 y 10 días hábiles.

**El punto clave**: la verificación de negocio completa **no es obligatoria para empezar** — solo es necesaria para levantar el límite. Sin verificar, queda un tope de **250 conversaciones iniciadas por el negocio cada 24 horas**, que para el volumen de un comité vecinal probablemente sea más que suficiente indefinidamente. Y como el comité casi seguro no es una entidad legal registrada (sin RUC/constitución formal), la verificación completa sería difícil de conseguir de todas formas — pero no se necesitaría.

En resumen: crear la cuenta y el número dedicado es relativamente sencillo (un par de horas de configuración); lo complicado (documentación legal, coincidencia exacta de datos) solo aplica si se quiere levantar el límite de 250/día, y probablemente no haría falta.

## Pregunta

con una cuenta Meta Business Manager, ¿como podríamos automatizar la lectura periódica y memorización del contenido de los chats?

## Respuesta

Antes de la parte de automatización hay una limitación fuerte que cambia el planteamiento: **el Cloud API no tiene un modo de "leer periódicamente"** — no es polling, es webhooks: se registra un endpoint HTTPS propio y Meta empuja cada mensaje en tiempo real a medida que llega. No existe un endpoint para "traer los últimos 7 días de conversación" retroactivamente.

Y hay algo más importante: **con una cuenta Business normal, el bot no puede unirse ni leer el grupo de WhatsApp existente de los vecinos.** La API de Grupos de WhatsApp solo está disponible para cuentas con **Official Business Account** (el check de verificación superior), que exige 3–5 artículos de prensa orgánica sobre la marca, señales de marca pública y una revisión de semanas — inalcanzable para un comité vecinal voluntario. Sin ese estatus, el número de Business API queda limitado a conversaciones 1:1, no a grupos.

**Lo que sí es realista automatizar**: el número dedicado del comité funcionando como un contacto 1:1 al que los vecinos escriben directamente (no dentro del grupo). Ahí sí:

1. Meta envía cada mensaje entrante a un webhook en tiempo real.
2. Un servicio Python (necesita estar corriendo permanentemente con un endpoint HTTPS público — no un script que se ejecuta cada tanto) recibe, guarda y opcionalmente resume cada conversación con un LLM.
3. Esas conversaciones acumuladas quedan como base de consulta para que el agente responda preguntas futuras basándose en lo ya respondido.

**Cómo encaja con el resto**: el grupo existente sigue funcionando igual entre vecinos (nadie automatiza eso); el histórico de ese grupo se sigue nutriendo por exportación manual periódica. El bot 1:1 sería un canal *adicional* — para quien prefiera preguntarle directo al agente en vez de buscar en el grupo — y ese canal sí se alimenta solo, sin pasos manuales, porque ahí el webhook sí funciona nativamente.

**Tradeoff a tener en cuenta**: este bot 1:1 requiere infraestructura corriendo 24/7 (servidor o función serverless con HTTPS), no algo que se prenda y apague — es un compromiso operativo real para un proyecto voluntario, aunque puede resolverse con algo mínimo (ej. una función serverless gratuita).
